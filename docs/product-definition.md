# Product Definition and Completion Contract

**Status:** normative product scope

Frameshift is Conjunct's first modular reference product and integration proof
of concept, with an independent native macOS controller,
durable host core, deterministic renderer, universal still-frame protocol,
frame agents, display adapters and qualified interoperable assembly profiles.
Its companion platform composes exact components and produces visual procedures
and an independent parts/shopping list. Conjunct is the planned generic engine;
it owns those generic composition, comparison, report, list and instruction
semantics. Its inspected cohort does not supply a qualified runtime package.
Frameshift retains product behavior and demonstrates the producer boundary
through executable fixtures.
The proof-of-concept role is an evidence target, not a production release claim.
The native product requirements below remain separately tracked.
Components retain their manufacturers' identities. This reference product does
not introduce Frameshift-branded assembled hardware or a mandatory assembler.

The portable host is also specified for Ubuntu amd64/arm64 and Raspberry Pi 5
Ubuntu Server arm64, with a separately qualified Nerves Pi 5 appliance role.
The [public installation guide](architecture/install-and-guide.md) and
[Linux host](host/linux.md) define those distribution claims. No Windows host
is specified. These separate controller-host targets do not authorize a Pi
inside a reference frame or a rear-mounted compute bulge.

## Product promise

A person can import or generate still artwork on a Mac, preview the exact
target interpretation, and send or schedule it on any paired compatible frame.
The system states whether work is queued, transferred, refreshing, failed or
physically displayed. Existing artwork remains visible through host, network,
transfer, refresh and update failures.

Ordinary import, rendering, transfer, display, library and playlist flows work
without a Frameshift cloud or AI account. Cloud generation and remote access
are optional explicit adapters. Complete installed thinness is mandatory;
there is no arbitrary universal display-size ceiling.

## Companion configuration and optional operations

The [build-platform specification](architecture/build-platform.md) defines the
companion product. Users visually choose Paper, Photo or Pixel components,
inspect fit and limitations, save a configuration, and print/export an exact
list with assembly and installation handoff. This requires no account, model
provider or purchasing integration and must be complete before transactional
integration is built.

The deferred optional **F extension**, currently on hold, describes admitted
external capabilities with explicit
counterparties, accepted terms, bounded consent, reconciliation, fulfillment,
returns and care. Product code does not select company rates, commercial
strategy, legal roles or countries. It consumes approved policy and financial
contracts. The local application remains independent.

Phoenix/Ash and phoenix-assets/Svelte 5 provide the product web host. Refpath
executes admitted product packs; Conjunct supplies generic composition/viewer
seams; Rivure is the financial owner for an enabled service profile; DocShell supplies
explanatory artifacts through a qualified integration. Bounded read-only diagnostics do not gain mutation authority.

## Complete installed flow

```text
source file / Photos / generated result
  -> decoded, normalized immutable master
  -> durable library, labels, provenance and recipe
  -> target preview and deterministic artifact
  -> paired frame selected by advertised capabilities and Forms
  -> authenticated direct push or sleeping-frame pull
  -> verified inactive storage
  -> desired state
  -> physical display adapter completion
  -> current state and host acknowledgement
```

Every arrow is part of the product. Tests that inject intermediate bytes or
call a simulator directly prove that boundary, not this installed flow.

## Universal frame contract

Frameshift compatibility is defined by W3C Web of Things semantics plus the
namespaced still-display vocabulary, never a vendor-name switch.

- A Thing Description declares interaction affordances, security metadata,
  protocol Forms and a capability instance.
- A Thing Model defines the reusable frame contract independently of endpoints
  and hardware.
- A Form binds a semantic operation to HTTPS, CoAP, MQTT or a future qualified
  transport profile. The host does not infer endpoints from a manufacturer.
- An artifact profile is the atomic compatibility unit for exact bytes. It can
  identify a qualified panel, controller, palette, packing, waveform, colour,
  gamma or power-limit revision without changing the interaction model.
- Unknown optional namespaced terms survive round trips. Unknown required
  profiles fail explicitly rather than being guessed.

Paper, Photo and Pixel are reference capability classes. Vendor-specific
adapters and measured profiles instantiate the universal contract rather than
narrowing it. Physical composition, paired-device admission and application
generation are separate identities and authorities.

## Definition of done

The Conjunct integration proof follows [CI-01–CI-08](architecture/conjunct-integration.md)
and the platform dependency gates. The installed product has the following
separate completion requirements; a successful integration proof cannot close
them. Optional service requirement 14 applies only to an enabled service profile:

1. The distributed macOS application embeds and supervises core/raster workers,
   uses authenticated local IPC, migrates data safely, survives sleep/restart
   and passes signing, hardened-runtime and notarization gates.
2. Supported image formats pass bounded decode, orientation and colour
   normalization into durable storage; restart needs no caller-held bytes.
3. Library search, labels, similarity, pinning, recoverable removal, trash/cache
   policy, provenance, recipes, playlists, schedules and audit export work
   through the installed UI and durable core.
4. Each enabled AI provider passes explicit capability, credential, privacy,
   cost disclosure, execution budget, progress, cancellation, result-validation
   and local-only isolation checks. Ordinary import/rendering remain usable
   without AI.
5. Rendering produces deterministic preview/wire artifacts for every claimed
   profile and measured visual evidence for each shipped hardware revision.
6. Discovery, pairing, identity custody, certificate rotation, authorization,
   direct push, sleeping pull, retry reconciliation and state observation work
   over actual authenticated transports.
7. Agents verify and atomically retain assets, execute still playlists,
   distinguish desired/current state, recover from interruption and run signed
   rollback-capable firmware.
8. The native UI passes keyboard/VoiceOver and accessibility-preference
   scenarios across compact, focused and Settings modes, preserves selected
   still-artwork task state between them, and never conflates accepted,
   transferred, refreshing and displayed states.
9. Versioned conformance evidence covers value/schema, runtime, binding, live
   transport, packaged application, firmware, hardware, security, lifecycle and
   upgrade/recovery profiles at their exact revisions.
10. Every released physical configuration has reproducible build records and
    measured electrical, power, thermal, optical, mechanical, mounting and
    interrupted-refresh evidence. Required independent evidence is complete
    for the actual release claim.
11. The public guide lists only qualified installs/profiles, runs simulation
    without remote code execution and hands non-secret choices to the native
    flow. Mac direct/Cask/Sparkle and each claimed Ubuntu/Pi package pass clean
    install/update/recovery and data-preservation tests. GitHub Actions builds
    self-contained universal Mac DMGs and target-specific Ubuntu DEBs from exact
    version tags; public archive bytes match their signed manifest. The canonical
    `frameshift.wotex.io` site provides `/download/`, latest qualified docs at
    `/docs/`, retained `/docs/vX.Y.Z/` and labelled unreleased `/docs/dev/`,
    generated from maintained Markdown/API documentation. Failed publication
    preserves the last verified site; development docs cannot imply availability.
    See the [installation contract](architecture/install-and-guide.md).
12. The visual builder/list satisfies BP-01–BP-09 and PB-01–PB-09, including
    unknown/custom facts, deterministic identity, provenance, explanations,
    cross-runtime parity and verifier evidence. Conjunct extraction preserves
    these guarantees and has explicit migration/consumer tests.
13. Research/model use satisfies BO-01–BO-08; metrics and bounded read-only
    diagnostics satisfy BP-10 and the diagnostics contract.
14. If optional external services are resumed and enabled, they satisfy the
    applicable BC-01–BC-10 requirements, including independent
    provider commitments, financial references, current authority, unknown
    outcome recovery, fulfillment, care and policy-driven data obligations.
    Activation cannot become a dependency for normal operation or the list.

## Status and release claims

The verification ledger records missing, partial or proven bounded claims.
Passing the currently implemented subset cannot redefine the complete product.

External credentials, permissions, independent reviews and physical measurements
cannot be fabricated in software. They remain named completion gates without
excusing missing implementable functionality, simulations or refusal paths.

Track software completion separately from external activation/release work.
The dependency order and deferred service scope are in the
[build-platform milestones](architecture/build-platform.md#milestones-and-evidence).
Company operating-model and economic research are not part of this product
contract; only the typed technical integration and evidence requirements are.
